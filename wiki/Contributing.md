# Contributing

Darwin is a research project with a deliberate set of constraints.
Contributions are welcome — please read this whole page first.

## The constraints (non-negotiable)

These are not style preferences. They are what makes Darwin
*Darwin*. Any change that violates them will be rejected on sight,
no matter how clever.

1. **No external LLM in the reasoning path.** The DLM is a renderer;
   the parser, the planner, the causal model, the concept index, the
   self-modification engine, the dream loop, the experiment engine,
   the discourse planner — none of these may call out to a neural
   model. See [Philosophy](Philosophy.md).
2. **No contamination of training data.** Darwin's *thinking* is not
   generated by another model and then imitated. See
   [Training Data Strategy](Training-Data-Strategy.md).
3. **No silent network calls.** Anything that talks to a process
   outside Darwin (Ollama, llama-cpp, transformers, future
   integrations) must:
   - have its own backend module with a clear interface,
   - be invokable only via explicit config (`--dlm gemma`,
     `--dlm-backend …`),
   - fall back cleanly when unreachable.
4. **Faithfulness is enforced structurally, not by trust.** Every
   user-facing output passes `FaithfulnessValidator` *and* the
   `ResponseCritic`. New rendering modes need new validator rules.

## Practical setup

```bash
git clone https://github.com/gh0st359/darwin
cd darwin
git checkout v2
pip install -e .
python -m unittest discover tests   # must be green before you start
```

No external runtime dependencies for the core mind. Optional DLM
backends are imported lazily so missing packages don't break the
default build.

## Branch + commit style

- Branch off `v2`.
- Keep commits focused. One commit = one logical change.
- The commit message should be the kind of thing the reviewer would
  paste into the changelog. First line: imperative, ~70 chars. Body:
  wrapped at 72, motivation first, mechanics second.
- Don't include emoji, AI-tool attribution, or boilerplate in commit
  messages, code comments, or PR bodies. The repo style is sober and
  technical.

## Testing

- New code needs tests. v2's `tests/test_v2.py` is the model.
- Tests must run without network access, without GPU, and in under
  10 seconds total for the full suite.
- For new daemon/protocol surface area, mirror
  `tests/test_brain_daemon.py`: spin up a daemon on a free port,
  drive a `DarwinClient`, assert. Always shut the daemon down in a
  `finally`.
- Don't mock things you can run real. The whole codebase is small
  enough that real components work.

## Code style

- Pure stdlib for core paths. Third-party imports are allowed only
  inside DLM backends and tests; they must be lazy and optional.
- Type hints everywhere. Dataclasses for record types.
- `dict[str, Any]` is fine; over-typing wire formats just slows
  iteration.
- Prefer explicit names. The architecture has many moving parts;
  shorthand makes it harder to follow.
- No comments that explain what the code does. Comments only for
  *why*, and only when the why is non-obvious.

## Adding a new background loop

1. Add `_loop_<name>` to `DarwinRuntime`. Take the lock; do work;
   return a `RuntimeEvent`.
2. Add an entry to `loop_intervals` defaults in `__init__`.
3. Add a `BackgroundLoopSpec(...)` in `start()`.
4. Add a test in `tests/test_v2.py` that drives the loop method
   directly and asserts the expected payload appears in
   `runtime.last_<state>` and in the event stream.
5. Optionally add a `/<name>` chat command and a slash-command branch
   in `cli.py` + `server.py` so users can trigger it on demand.

## Adding a new discourse mode

1. Add a `_xxx_plan` method to `DiscoursePlanner`.
2. Route to it from `plan(...)` based on a clear signal (speech act,
   focus terms, packet state).
3. Make sure `_enrich_plan` still runs after your method returns.
4. Add or extend a `FaithfulnessValidator` rule if the new mode
   imposes a new structural promise on the output.
5. Test: a `Phase0InstrumentationTests`-style assertion that the new
   mode produces a plan whose `to_dlm_payload()` shape is what you
   intended.

## Adding a new DLM backend

1. New method on `GemmaDLM` (or a new class for radically different
   backends). Lazy import.
2. Honour the same system prompt + plan-payload contract.
3. Run output through `FaithfulnessValidator`. Do not relax it.
4. New tests should *not* require the backend to be installed; mock
   the network/IO at the seam.

## What gets a PR merged

- `python -m unittest discover tests` is green.
- New code has tests that fail without it.
- Diff is small enough to reason about in one sitting.
- Commit message + PR description explain the *why*.
- No additional runtime deps to the core mind.
- Passes the constraints above.

## What gets a PR rejected

- "Let an LLM do it" anywhere outside the DLM.
- Removing or weakening the `FaithfulnessValidator`.
- Adding code that uses a network call without a fallback.
- Adding "AI-generated"-style boilerplate to docs, commits, or code.
- Large mechanical refactors with no behaviour change.

## Reporting bugs

Open an issue with:
- the command you ran
- the full output (including the brain terminal if relevant)
- the contents of `darwin_runtime_state.json` if it isn't private
- the failing test, if you have one

A bug report with a failing test is the highest-leverage thing you
can do.
